## 已确认的问题

此前实物记录（[0.8.22](cube-lite-freeze-diagnosis-0.8.22.md)、[0.8.23](cube-lite-ui-contention-0.8.23.md)）出现过网络及 UDP 会话有回复、灯光控制没有回复的状态。0.8.56 运行路径仅查会话心跳，并用本地 `on` 占位继续保持在线，不能发现执行器失去响应，仍会持续发送像素。

另用回执乱序测试复现：同步控制指令先读走待处理的异步心跳回执、再读自己的回执，会遗留已经完成的 pending 心跳，随后误报超时并新建会话。

维护连接还会创建一个临时 Cube UDP 会话验证亮度，关闭本机 socket 后立即创建持续灯效会话。本地 socket 关闭不等于设备已销毁会话。这与第三方同型号作者最近实测报告的「混用控制与流会话可冻结设备」对应，但尚未在本机建立卡死前后的因果对照。

## 重启路径的新增证据

- 厂商 [UDP R2 协议](https://raw.githubusercontent.com/Yeelight/Yeelight-Chroma-Connector/master/Yeelight_Inter_Operation_Spec_UDP_R2_en.pdf) 定义最多 4 个 UDP 会话，超出替换最老会话；4 次心跳缺回复是客户端判定链路异常的规则，不是设备回收会话的 TTL。没有找到主动删除会话命令，不能声称固定等 11／41 秒能清空旧会话。
- 退出清屏会调用 `prepare_frame`，尚未首次显示的客户端反而会在退出期间激活 direct、升亮、开灯；真实 worker 回归已复现。正常退出原先也仅发送无 ACK 黑帧，没有确认关灯。
- 本机停止 Cube 自动连接后，独立诊断先后关闭／重建 3 个 socket，绑定同一源端口、使用原 token，心跳均得到真实确认，约 9–14 ms。随后两个独立 Python 进程使用持久缓存重开同一端口，也仅通过 keepalive 成功恢复，未申请新会话；请求 ID 分别为 65537 与 131073。因此已验证可跨进程复用网络 endpoint，而非依赖 FD 或猜测会话过期时间。

## 修复

- 每个已确认物理设备单独私密保存 UDP 端口、token 和预留请求 ID 段；重启优先绑定原端口并要求旧 token 的真实心跳回执。失效时才在同一端口进行一次新握手；原端口仍有占用时拒绝随机另建并行会话。缓存原子写入，文件 0600、目录 0700；每次预留 65536 个 ID，避免崩溃后重用编号及逐帧落盘。DHCP 地址变化仍复用该物理设备的端口。删除设备只清除该设备缓存；重置 APP 清除缓存目录，删除失败保留设备供重试。
- 连接验证只将主亮度设为 1；首次显示按 power off（ACK）→主亮度 100（ACK）→direct（ACK）→黑帧（sent）→power on（ACK）→最新期望帧执行，避免在旧画面亮着时先升至满亮。用户实体确认低亮关灯后激活 direct 仍全暗，保持关灯仅升亮至 100 后也仍全暗。
- Cube 退出时不会初始化尚未开始的 direct 显示；已开始时清屏，然后发送有回执的真实 power off。清屏失败也会尝试关灯；Beam 行为保持原样。
- 维护阶段使用已在本机验证可回执的 TCP `set_bright`，关闭后再启动唯一持续 UDP 会话；继续避免固件不回复的 `get_prop`。运行期间的帧、心跳和控制全部复用同一 UDP socket/token。
- 每 60 秒异步发送当前渲染所需的主亮度 100，必须收到该请求 ID 的 `ok`；帧仍按原来的 10 FPS 调度，不等待探测。探测与回执后均使重复帧缓存失效，当轮重新渲染最新期望画面，覆盖亮度 setter 可能恢复的旧图。
- 会话与执行器回执统一分发，乱序、迟到的心跳不会被同步指令吞掉。控制探测同 ID 最多重试两次，总截止 2 秒；无控制回执时停止像素发送、标离线、记录失败原因，65 秒后重试，避免每 3 秒重复创建控制会话。
- 在线状态中的 `last_heartbeat`、`last_control_ack` 来自真实回执时刻。像素仍只标记 `sent`，不伪造显示确认。
- 静止及全黑画面最多每秒补发一次，保留 UDP 丢包恢复；动态更新上限仍为 10 FPS。
